一、实战任务概览与提交规范
针对本次大模型实战任务，会议明确了任务形式、提交要求及资源使用规范：
1. 任务形式与成果要求
独立仓库提交：学员需在 GitHub 创建独立开源仓库，无需像 Issue 那样提交 PR。仓库需包含完整的应用源码、环境配置及运行说明。
核心产出物：必须包含评测样本、评估脚本、结果分析报告（含场景选择理由、方案实现及典型模式挖掘）以及 2 分钟左右的 Demo 视频/GIF。
安全与合规：严禁在代码中硬编码 API Key 等密钥，需在 README 中标注项目属于“犀鸟活动”，与腾讯官方无关。
2. 资源与环境配置
模型调用规范：强制要求使用混元三模型（Hunyuan-3），不可自行训练或微调。支持通过 WorkBuddy 积分或腾讯云免费 Token 调用。
部署灵活性：学员可选择在 WorkBuddy 平台使用积分，或自行在 H200 等设备上部署混元三模型进行推理，无需进行 SFT 微调。
仓库公开性：最终提交的 GitHub 仓库必须是公开仓库，以便评审。
二、任务一：开放式场景构建与评估
该任务侧重于无标准答案的真实用户场景，重点考察评估体系的构建能力：
1. 场景选择与构建
场景多样性：可选择法律问答、医疗摘要、学术助手、金融分析等非标答案场景。鼓励基于真实用户数据（如高校食堂 App 数据）构造 Bench。
样本构造策略：需包含从简单到困难的样本，特别是模型解决不好的难点样本，以验证评估方法的区分度。
2. 评估体系设计
多维度指标：需设计覆盖证据可追溯性、专业术语正确性、安全合规等多个维度的评估方法，可采用 Rubric 打分或校验规则。
有效性验证：评估方法需能有效区分质量差异明显的输出，并与人工标注保持较高一致性。鼓励进行对抗性验证（如堆砌术语、增加篇幅）以检验鲁棒性。
三、任务二：可验证场景的过程评估
该任务针对有标准答案（Ground Truth）的数理代码类场景，重点考察对推理过程的监控：
1. 场景与目标
场景定位：适用于数学、物理等有标准答案的理科任务，或 Agent 执行代码、办公自动化等可验证场景。
评估重心：不单纯看答案正确性，而是重点评估推理链条的完整性、逻辑合理性（如跳步、循环论证、幻觉）及中间过程的正确性。
2. 技术实现路径
错误类型体系：需建立一套针对推理错误的分类体系，利用沙盒环境或 Agent 访问权限进行过程监控。
应用形态：可在混元三模型基础上包装 Agent 框架，构建 App 应用，进行端到端的评估；若场景简单，也可直接对裸模型进行评估。
